01

装配层

PROFILE BUNDLE · CORDIS PATCH · OPT-IN

「智能体团队」在插件页里只是一个开关，落到磁盘上是 profile 里多了一层 bundle；落到运行时上，是四行 patch：禁掉全局 subagent 工具，插入 Team 服务、Team 工具与 Web 面板。没有运行时代码开关，也没有独立入口。

L1 · profile 的有序层

dsh.profile.bundles = dsh-base dsh-web-app … dsh-experimental-agent-team-profile
APPLY PATCH AFTER dsh-base
# cordis.patch.yml — 运行时内容就是这个 patch - id: tool-subagent-control disabled: true - id: tool-subagent-list-agents disabled: true - id: tool-subagent disabled: true - id: tool-subagent-fork disabled: true - insert: - id: agent-team name: '@deepseek-ai/dsh-experimental-agent-team' config: { maxMembers: 8, maxTasks: 256, maxMessageBytes: 65536 } - id: tool-agent-team name: '@deepseek-ai/dsh-experimental-tool-agent-team' config: { freshProvider: spawn, forkProvider: fork } - id: ui-agent-team name: '@deepseek-ai/dsh-experimental-client-ui-agent-team'

为什么禁用全局工具？ 默认工具目录保持简单；“委派”这条语义只在这层组合里由 Team 工具接管，避免同名工具彼此遮蔽。

为什么拆成三个插件？ 领域状态（服务）、模型可见面（工具 + prompt）、浏览器呈现（UI）各自独立，headless 可以只装前两个。

04

创建 Saga

PROVISIONING → ACTIVATION → ACTIVE · 名字永不复用

teammate 不是“凭空多出来一个 agent”。先持久化意图，再启动预留身份的 child，最后确认初始 prompt 已落盘才宣告 active。任何一步失败都留下 failed 而不是回收名字；冷启动用对账而不是重放 prompt。

05

消息投递

INBOX STEER · NOT A MAIL SERVER

Team 自己不存消息。发送 = 校验成员身份 + 加发送者前缀与 source，然后借用 Subagent 的 steer 路径写进目标 inbox；排序、持久化、去重都归目标 Agent。切换场景看三种结果。

Outcome

Lead 是始终活的会话：直接 root.steer(createUserMessage(...))，消息留在 Lead 的 inbox，在最近 step boundary 被看到。

模型看到：Team message from reviewer: …
What Team guarantees

成功 = 已进入目标 inbox（inbox 接收）。Team 不保留未接收意图、不在重启后重试、不对显式重发去重；冷恢复时先复用持久会话，再追加消息。

Design boundaries明确不做的事
  • 01单进程、共享 checkout。没有 worktree、没有文件锁；Bash / codegen 可绕过版本检查，最终 diff 仍由 Lead 负责。
  • 02owner 不自动释放。idle、interrupt、进程退出都不会把任务放回板；崩溃 owner 会永久留住任务。
  • 03发送无重试、无去重。成功只代表进入 inbox；未到达目标的历史消息不会被补投。
  • 04扁平 roster、实验性。无嵌套 Team、无重命名、名字永不复用；约定在孵化期可自由变更。
